AI contract testing · Phase 1 solution concept

Catch breaking API changes before they reach staging

Contract testing already does this. Almost nobody adopts it, because writing the contracts costs weeks per service and the provider side costs more than that.

ContractPilot reads both repositories, proposes the contracts and the tests, runs them, and hands over only what passed for the right reason. Everything it proposes points back at the line of code it came from.

01 · The problem

Contract testing works. Adopting it is what teams cannot afford.

The established tools run contract tests well. The expensive part comes before that: finding every call between services, writing the expectations by hand, and seeding the provider so verification can run at all.

Weeks before the first test runs

A service with a few hundred endpoints is weeks of hand-written declarations. That cost lands before the team has seen a single contract catch anything.

Provider state is where it stops

given order 42 exists means seeding data inside the provider. This is the step people skip, and skipping it means verification never runs.

Hand-written contracts go stale

Code moves, declarations do not. A description nobody regenerates passes its comparison while describing a service that no longer behaves that way.

So one team ends up doing it for everyone

When adoption costs that much, a central team absorbs it service by service. That team becomes the bottleneck, and the service teams never own the result.

02 · Proposed solution

Code finds the calls. The agent writes the tests. The run decides.

ContractPilot never asks a model to invent an API. Every interaction starts from code it can point to. The agent supplies what static analysis cannot: what a field means, and how to set up the provider state a test needs.

Read what the contract suite in this repository is actually comparing today, and report the parts that are silently checking nothing.

Interaction map

One language-neutral model of every request, response, and the fields the consumer actually reads. Each entry carries its file and line.

the artifact every later step reads

Propose

A declaration a person can review as a diff, which the tool turns into a spec and a contract on its own. Consumer side and provider side.

output is code the team owns
4

Run and repair

Compare the result against the provider's own contract, not against the mock the same agent just wrote. Feed each failure back and retry. Still failing, report it unresolved.

the loop that makes the output trustworthy

No expectation without a source reference. No proposal without a run. No output larger than a person will read.

The third rule is the one that gets left out, and it decides whether a team keeps using any of this. Section 04 is about why.

03 · Both sides of the contract

One tool, two jobs, and only one of them is unsolved

The consumer half already has a commercial implementation, so ContractPilot calls it. The provider half is only partly served, and the part nobody serves is the one that stops adoption.

Consumer side

integrate

"This is what I call, and what I need back."

  • Find each outgoing call and the request it sends.
  • Follow the response through the code to see which fields get used.
  • Write the contract with flexible matchers rather than fixed example values.
  • Emit the consumer test that produces the contract file.
  • PactFlow already ships the generation step. ContractPilot supplies the discovery it cannot do, and calls it.

Provider side

build

"Prove I still give every consumer what it needs."

  • Generate the verification test that replays each consumer contract.
  • Read the data layer to write the state setup that makes it runnable.
  • Flag fields the provider no longer returns, or returns with a different type.
  • Show which consumers would break before an endpoint changes.
  • Existing tooling emits the shape of a state handler. Working out what it should actually seed, from the service's own data layer, is the part nobody covers. PactFlow's own FAQ lists provider verification as "planned for future updates".

04 · Why this time is different

Generated contract tests have failed before, and not for the reason people assume

This is not a new idea, so the place to start is what is already known about how it goes wrong. None of the three failures below is an accuracy problem.

What goes wrong

  • Output nobody reads. A generator that emits a whole specification for a whole service produces more than a team will review. No review means no ownership, and no ownership means nobody maintains it.
  • Passing for the wrong reason. A consumer test run against a mock the same generator wrote will pass. It has proved that the generator agrees with itself.
  • A check people route around. Staleness detection built on file hashes fires on every refactor. A gate that is noisy rather than wrong still ends up switched off, and then it guards nothing.

What that implies

  • The unit of output is a diff a person reads in a minute, never a service.
  • The thing that judges the output cannot be the thing that wrote it. It has to be an independent comparison against the provider's own contract.
  • A judgement about whether an API changed has to come from reading the change, not from hashing the file it lives in.
  • Nothing is committed without a human accepting it.

Deliberately not in a first version

  • Message and event contracts.
  • Contracts derived from live traffic.
  • A hosted service, a pull-request bot, or repository permissions.
  • Replacing a contract pipeline a team already runs.
  • Gating a deployment on the result, which is an agreement between teams rather than a tooling gap.

Which half is the agent, and which half is code

The previous generation of this idea had it backwards: a model produced the mechanical artifact, and nothing independent judged the result. The split below puts the model on every step that needs judgement and code on the two that do not.

StepDone byWhy
Find the call sitesagent The alternative is a parser with a special case for every way a URL can be written

This is why the command-line tool is built before the agent instructions. The agent calls it to find out whether it was right, which makes it the oracle rather than a way to ship.

05 · How accuracy gets measured

The failure modes repeat, so they can be tested for

The usual answer to "how do you know the model got it right" is a confidence estimate. There is a better one available. Every way a generator produces a wrong contract has a shape, and a shape can be written down as a test case.

The regression suite

6 runnable cases in a first version
invented value

A loosely typed field lets the generator choose something plausible. The provider accepts one spelling; the generated contract asserts another.

expected: narrow the type from provider evidence, then re-run

null for a required body

An untyped request body becomes a literal null, which the provider's schema does not admit.

expected: request.body.incompatible, and the proposal is withheld

dropped path segment

Generating a negative case for PUT /path/{param}/suffix, the generator substitutes the parameter and loses the trailing segment, so the request names a route nobody serves.

expected: request.path-or-method.unknown. An unknown path short-circuits the comparison, so this is the case where the artifact half of the pass rule does the work

green against nothing

A green comparison is not always a comparison that happened, and the reasons are different kinds of thing. A response declared as a multi-branch union accepts a body that fits any branch, which is a property of the comparator. An interaction whose path the provider has not declared is skipped whole, which is a publishing state and ends the day they publish it. Telling those two apart is the point: one is a limit to design around, the other is a queue of work belonging to someone else.

reproducible in a few lines against @pactflow/openapi-pact-comparator · reporting them is step 1, not step 4

the pass rule

A case is green only when both halves agree: the wrong value is absent from the generated artifact, and the comparison against the provider's contract reports nothing. Either half alone has passed before while the contract was wrong.

the suite is the acceptance gate for the agent instructions

Failures stay visible

A test that cannot be made to pass is listed as unresolved with the reason. Hiding it is how a suite stops being trusted.

Standard formats only

Output is Pact-compatible, so existing brokers keep working and there is nothing to migrate off.

06 · How it plugs in

A command your team runs, and instructions your assistant reads

Two files in a repository you already own. No hosted service, and no change to the application code.

C

The command

diagnose reports what the contract suite compares today. propose writes a declaration for review. verify runs the tests and the comparison, and exits non-zero when either fails.

deterministic · same input, same output
A

The instructions

A plain-text file a coding assistant reads. It carries the judgement steps: where the call sites are, which fields matter, how provider state is set up in this codebase.

assistant-agnostic · reviewed like any other file
CI

The pipeline runs one of them

CI calls verify and nothing else. A pipeline cannot ask a question, read a diff, or decide that a field was renamed on purpose, so the judgement half stays at the developer's desk where someone can answer.

a deterministic gate is one you can trust to block

What your repository needs already

A published contract on each side. A first version compares what a consumer declares against what a provider publishes, so a service with neither has nothing to diagnose yet. That entry path is a later version, and saying so now is cheaper than a team finding out.

What it does not need

No repository permissions, and no running provider instance for the first command.

Comes later

A pull-request bot that posts the drift report, and anything else needing hosting or write access. Worth it only once a team trusts the output.

07 · What leaves your repository

The half that judges never leaves your machine

An agent that reads your source is the first thing a team's lead asks about, so it gets a section of its own.

Only the files it names

The agent sends what it needs for the step it is on, and every proposal lists those files. The repository is never uploaded.

The verification is local

The comparator is an MIT-licensed package with no licence key and no network call, so checking a contract against a specification happens entirely on your machine.

A self-hosted model where required

For work under NDA the judgement steps can run against a model you host, with no change to the command or the instructions.

Nothing is committed silently

Proposals are files on a branch. A developer accepts, edits or rejects them, and the result is ordinary test code the team owns.

08 · What already exists

Built on PactFlow, not against it

The broker, the comparator and the consumer test generator all exist already, and ContractPilot calls them. Rebuilding any of them is the fastest way to make this undeliverable. Checked October 2026 against each vendor's own documentation.

SmartBear MCP server Exposes that generation and review to a coding assistant as tools. integrate No reason to write our own surface for the consumer half.
Spec-driven and traffic-driven tooling Other tools run an existing specification as the executable contract, or derive tests from recorded traffic, with no generation step at all. defer Where a maintained specification already exists, that route is cheaper, and the honest thing is to say so rather than compete with it.
Provider state generation Partly covered. Existing tooling emits handler stubs and can read known state names from a broker. None of it works out what a handler should seed. build The narrow gap is deriving that from the service's own data layer, and it is the step teams skip.

Vendor claims are taken from their own pages and are not independently verified. The conclusion is narrow and checkable: only the provider half and the run-and-repair loop are not available to buy. One gap, on someone else's platform.

09 · Delivery plan

The oracle first, then the agent that answers to it

About four to six weeks with one or two engineers. The main risk is not code generation, which is the cheap part. It is accuracy: how often a proposal survives without a hand edit, and whether it failed for the right reason.

Stage 0 · Week 1

The oracle

The command that compares a contract against a provider's contract and reports what is silently checking nothing. Read-only, needs no running service, and is the whole of a team's first day.

Stage 1 · Weeks 1–2

The mechanical half

Turning a declaration into a specification and a contract, deterministically, so the same input always gives the same output. Plus the interaction map that feeds it.

Stage 2 · Weeks 3–4

The agent, and the provider half

The judgement steps, graded against the oracle from stage 0, and provider state setup read from the data layer. The part no tool currently does.

Stage 3 · Weeks 5–6

Someone else's turn

A team we do not sit with integrates it from the documentation alone. That trial is the result, not a demonstration at the end of one.

Two things are not settled. Which team runs the first trial, and which of the two contract-testing modes a first version targets. The second follows from the first, and neither can be answered by picking one of our own services.

Trust every deploy between your services

ContractPilot is at the concept stage. The generation half of this idea has been tried before, which is why the plan spends its weeks on the two things that attempt showed were missing: the provider side, and an independent way to tell a correct contract from one that merely passes.

Two numbers A first version succeeds if a team we do not sit with gets a passing contract from the documentation alone. How long that took, and how many times they had to ask us: those two are the result, and no threshold is set for them yet.
