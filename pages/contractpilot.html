Catch breaking API changes before they reach staging

Plug ContractPilot into a consumer or provider repository. It reads how services actually call each other, writes contract tests for both sides, runs them, and only proposes tests that pass for the right reason.

The problem

Contract testing works. Writing the contracts is where teams give up.

Tools like Pact and Spring Cloud Contract run contract tests well. The hard part comes before that: finding every call between services, writing expectations by hand, and setting up provider state so verification can run at all.

Slow to start

A team with dozens of service-to-service calls needs days of manual work before the first contract runs in CI.

Provider state is painful

"Given order 42 exists" means seeding data in the provider. This setup is the part people skip, so verifications never run.

Contracts go stale

Code changes, contracts do not. Broken integrations show up in staging or with a customer instead of in the pull request.

Proposed solution

Code finds the calls. AI writes the tests. The test run decides.

ContractPilot does not ask a model to invent an API. Every interaction comes from code it can point to. AI fills in what code analysis cannot: field meaning, provider state and edge cases.

1

Scan the code

Parse both repositories to find where services talk to each other.

Consumer · HTTP clients, Feign, axiosProvider · controllers, routes, DTOsOptional · OpenAPI spec
2

Interaction map

One language-neutral model of every request, response and the fields the consumer actually reads. Each entry links to file and line.

3

Generate tests

Consumer tests and contract files on one side. Provider verification and state setup on the other.

4

Run and repair

Run the tests for real. On failure, feed the error back and retry a few times. Still failing? Report it, don't hide it.

No expectation without a source reference. No proposed test without a run.The run-and-repair loop is what stops tests that pass for the wrong reason.
Both sides of the contract

One tool, two jobs

Consumer side

"This is what I call, and what I need back."

  • Finds each outgoing call and the request it sends.
  • Follows the response through the code to see which fields are really used.
  • Writes a contract with flexible matchers (type, format, regex) instead of fixed example values.
  • Generates the consumer test that produces the contract file.
Provider side

"Prove I still give every consumer what it needs."

  • Generates the verification test that replays each consumer contract.
  • Reads the data layer to write provider state setup ("given order 42 exists").
  • Flags fields the provider no longer returns, or returns with a different type.
  • Shows which consumers would break before an endpoint changes.

Plug in

Start from the command line. Grow into the pull request.

The core

  • contractpilot init detects the stack and test framework.
  • scan builds the interaction map.
  • generate writes and runs tests.
  • verify runs everything in CI.

Why start here

  • Works on any machine and any CI.
  • Output is plain test files the team owns.
  • No hosted service needed for the first version.

Inside the coding assistant

  • Exposed as an MCP server, so an AI coding agent can call scan, generate and verify as tools.
  • "Add contract tests for the payment client" becomes one request.

Why it helps

  • The agent gets the interaction map with source references, not raw guesses.
  • The same run-and-repair loop applies, so results match the CLI.

On every pull request

  • Diff the change, find affected contracts, and comment with the drift report.
  • Suggest contract updates when a change is intentional.
  • Publish contracts to a broker so each side verifies the other.

Comes later

  • Needs hosting and repository permissions.
  • Only worth it once the team trusts the CLI output.
Guardrails

Generated tests only help if people trust them

No invented fields

Every expected field and status code must link to source code. Anything without a reference is dropped.

Human review

Tests are proposed, never committed automatically. The team owns the output as normal test code.

Minimal code sent to AI

Only the relevant snippets go to the model, with a self-hosted model option for projects under NDA.

Standard formats

Output uses existing formats such as Pact, so there is no lock-in and existing brokers keep working.

Delivery plan

Start with one stack and REST only

About 4–6 weeks with 1–2 engineers using AI-assisted development. The main risk is not code generation. It is accuracy: how often generated tests pass without hand edits.
