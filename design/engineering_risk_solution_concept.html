Phase 1 Solution Concept
From fragmented signals to prioritized action

Engineering delivery risk should be visible before it becomes a surprise.

Turn Jira, pull request and CI signals into a prioritized, explainable action list for the people monitoring delivery — while keeping risk decisions deterministic and auditable.

Monitor / PM / Project Owner view Rule-first, AI-second Evidence-backed Security before real data
01 · The problem

Risk exists across systems, but people must connect it manually.

A project owner can see that a ticket is late in Jira, but still needs to inspect review status, CI results and ownership elsewhere before knowing what actually needs attention.

1

Fragmented evidence

Ticket state, review state and build state live in different places. The real delivery story is spread across tools.

2

Manual prioritization

People repeatedly open tickets, PRs and CI runs to decide which issue deserves attention first.

3

Alerts without action

Knowing that something failed is not enough. A monitor needs the cause, urgency, responsible role and next step.

02 · Proposed solution

A deterministic risk engine turns scattered engineering facts into an actionable monitoring view.

The system does not ask AI to guess whether a risk exists. Rules decide the finding from source evidence. AI is optional and only explains or rewords already-validated results.

Engineering sources

Read the minimum fields needed from delivery systems.

Jira · status, due date, owner, sprint
PR · review state, age, author
CI · result, failed job/step, category
→

Deterministic risk engine

Correlate related work and apply documented rules. Same input + same snapshot time = same result.

→

Actionable finding

What is wrong, why it matters, severity, responsible role, next step and expected outcome.

→

Optional AI explanation

Translate verified facts into concise language. AI cannot create or change the underlying risk decision.

Code decides the truth. AI explains the truth.Risk decisions remain reproducible, testable and traceable to source evidence.

04 · What changes from Phase 0 to Phase 1

Move from detection to actionability.

What Phase 0 proved

  • Cross-source Jira + PR + CI correlation works.
  • Findings are deterministic and evidence-backed.
  • Jira-only can miss the stronger cross-source conclusion.
  • The core finding was useful to both validation participants.

What Phase 0 did not prove

  • Complete delivery-risk coverage.
  • Production integrations or live data.
  • A severity model.
  • Real LLM quality/cost.
  • Production security/deployment.

Core Phase 1 additions

  • Realistic noisy data and more risk patterns.
  • Deterministic severity / priority.
  • Structured CI failure cause.
  • Responsible role + next step + expected outcome.
  • PM/monitor overview and drill-down.
  • NEW / RECURRING / RESOLVED history.

Intentionally not built yet

  • Production live integrations.
  • Slack / Teams / email delivery.
  • Production DB, auth or RBAC.
  • Deep CI-log root-cause analysis.
  • Predictive risk / ML.
  • AI-generated rule creation.
05 · Security is an entry condition, not an afterthought

Real data only comes after the data boundary is agreed.

The meeting identified NDA, customer-data and deployment concerns as potential blockers. Phase 1 therefore treats security/deployment as an early design gate.

Data minimizationCollect only fields required for risk detection. Exclude unrestricted descriptions, comments and source code by default.
Access & storageDefine customer-hosted vs centrally hosted options, access control, encryption and retention before real integration.
AI boundaryExplicitly define which fields may be sent to an external model. Customer data is not used for model training without separate approval.
Validation firstUse synthetic or sanitized data until the security/data decision is reviewed.
06 · Proposed delivery sequence

Phase 1 is a focused validation phase, not the finished platform.

For the focused scope below, a more realistic target is approximately 4–6 weeks with 1–2 engineers using AI-assisted development. The main schedule risk is not coding speed; it is rule definition, data availability, security decisions and user validation.

Stage 0 · Week 1

Confirm boundaries

Target persona, security/data policy, available fields and the small set of Phase 1 rules.

Stage 1 · Weeks 1–2

Realistic foundation

Noisy multi-item data, schema update, CI failure category and prioritized findings.

Stage 2 · Weeks 3–4

Make findings actionable

Reason, severity, responsible role, next step, expected outcome and basic history.

Stage 3 · Weeks 5–6

Validate and harden

Monitor-facing view, non-builder review, fixes, security/design decisions and optional real-data mapping spike.
